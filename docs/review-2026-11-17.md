# Code review, 17 November 2026

A new review of the whole of Explorer (`src/`, never `vendor/`), started from scratch. It looks for three things: simpler code, a better split into modules, and less work on hot paths. Performance is reasoned from the code, not measured.

This file holds the map (phase 0), the proposed target layout (phase 1), the performance findings made while mapping, and the plan for the deep dives (phase 2) and the synthesis (phase 3). The code is cited by name, not by line number.

**Status.** Phases 0 and 1 are done. The target layout below waits for the owner's approval: phase 2 starts only once each item of it is accepted, changed or dropped.

**Decided before this review, not to be reopened:**

- The import style stays as `AGENTS.md` states it (full paths at module level, no re-exports).
- No new type aliases, e.g. none for `GlobalData<AppState, AppSignal>`.
- The 100 ms spinner tick runs for the whole session (`docs/review-2026-11-second-pass.md`, C1).
- `fmt-md .` formats the whole repository (same file, C2).
- The whole repository stays in memory (`AGENTS.md`, project goal).
- The loader, watcher and report-render measurements of `docs/review-2026-11.md` (step 22 and phase 3) stand: those paths are not reviewed again unless the code changed.

### Layers

The layering of `AGENTS.md` holds: no module of `util`, the core or `agent` imports `tui` (the one mention, in `config.rs`, is a doc comment). `signal` sits in the core. `loader` and `lsp` meet where `AGENTS.md` says they do, and also in `lsp/mod.rs` and `lsp/worker.rs`, which name `loader::LoadedFile` and `FileKey` (the same layer, but `AGENTS.md` does not list them). The previous review fixed the layer violations, so what is left is inside `tui`, and inside `agent`.

What the import graph shows (non-test code, counted with a script over `crate::` paths):

- **`tui::state` is a hub.** It imports 17 modules, `agent::turn`, `agent::mcp`, `command_line`, `session` and `after_agents` among them, and most panes import it (`preview` 29 times, `git_log_pane` 27, `discussion` 25; `report_pane` not at all). `AppState` has 52 fields, all `pub`.
- **Widgets are not leaves.** `widgets::title_row` takes `&mut AppState`, and `widgets::fuzzy_picker` takes `state::FuzzyPickerState`, `&AppState`, `&mut PaneManager` and `&Window`. A widget should take values, not the application state.
- **The turn lifecycle lives in a pane.** `panes/discussion/launch.rs` names `agent` 20 times (7 of them `agent::commands`) and `conversation` 23 times. Starting a turn is in `discussion/launch.rs`, the queue in `discussion/queue.rs`, the end of a turn in the `TurnFinished` arm of `app/signals.rs` (since moved to `DiscussionComponent::turn_finished`, see L4), the stop at exit in `app/mod.rs` (`stop_running_turns`), and the command after the queue empties in `after_agents.rs`. The state is split the same way: `running_turns`, `queued_turns`, `spinner_tick`, `after_agents`, `after_agents_grace` and `next_after_agents_run` are separate fields of `AppState`.
- **`pane_manager` holds types and helpers of other panes.** `DocPart` (the Discussion's), `SelPoint` and `TextSelection` (the preview, the terminal and the Discussion) live in `pane_manager.rs` beside the layout, as do `block_scroll`, `ranges_scroll_target` and `format_line_ranges` (the preview's line highlights).
- **Every pane re-derives its own window.** Six panes call `pane_component::pane_slot(self.id)` and then `pane_manager.slot_window` to learn what they show (`file_key`, `terminal_id`, `window_id`), although `PaneComponent` already matched on that window to pick them. Four panes (preview, terminal, git log and conversation tree) also keep their own copy of the content geometry (`content_origin_row`, `content_col_count`, …), which `PaneComponent` keeps too.
- **Window kinds are matched everywhere.** `Window::` appears in non-test code 50 times in `pane_component.rs`, 30 in `window_picker.rs`, 16 in `session.rs` and 14 in `focus.rs`; `pane_manager.rs` names it only in its tests. `PaneComponent` holds one instance of each of the ten pane components, for each of up to 16 slots, and matches the ten window kinds again in `render`, `handle_event` and `render_title_row` (ten arms each), and in `apply_scroll`, the mouse path (six arms, one of them grouping five kinds).
- **Per-window state is spread over parallel maps.** `terminal_panes`, `git_logs`, `discussions`, `reports` (by window id), `commit_diffs` (by object id), `preview_inputs`, `search`, `highlight_ranges` (by `FileKey`), with `pending_terminals` and `terminal_to_preview` beside them. Closing a window has to know which maps hold its state (`focus::close_window`), and so does `session.rs`.
- **Inside `agent`** there are cycles between siblings: `agent_loop` ↔ `subagent`, `tools` ↔ `subagent`, `tools` ↔ `mcp`, and `context` → `agent_loop`, which closes a loop through `subagent` (`agent_loop` → `subagent` → `context`). They compile, but they mean none of these files can be read alone.

## Phase 1: target layout

Each item is a proposal for the owner to accept, change or drop. They are ordered so that each one makes the next simpler, except that L3 and L6 come after L7; the order of work is in phase 3.

- [x] **L1. A resolved UI palette on the theme.** Today 73 call sites outside the tests look up a UI color by string (`theme.ui_fg("ui.text")`, `ui_bg("ui.selection")`, …), each with its own fallback, and the fallbacks disagree: `ui.text` falls back to `(170, 170, 200)` in eleven places, `(212, 212, 212)` in three (two in the file preview, one in the git log) and `(120, 120, 160)` in two; `ui.selection` to `(50, 50, 90)` in the preview and the Discussion but `DEFAULT_SELECTION_BG` in the terminal, the git log, the fuzzy picker, the title row and the tree; `ui.background` to `(15, 15, 25)` in the preview but `DEFAULT_BG` elsewhere. Proposal: `HelixTheme` resolves once, at load, a `Ui` struct of plain `RgbValue`s (background, text, dim text, selection, line number, status line, error, warning, marker, …), each with one fallback chain. Every render reads fields. Simpler, one color per role across panes, and no hashing on the frame path (the preview looks `ui.text` up once per painted segment). The fallback constants of `title_row.rs` move into `theme.rs`.

  Done, extended to the terminal's colors. The 16 color names Helix gives the terminal's palette (`red`, `light-gray`, …) resolved to nothing, so 30 bundled themes lost styles to Explorer's fallback colors; `base16_terminal`, `base16_transparent`, `term16_dark`, `term16_light`, `ttox` and `ttox_soft` lost nearly all of theirs. `RgbValue` cannot say "palette entry 13" or "the terminal's default", so the palette is of `theme::Color` (`Rgb`, `Ansi`, `Default`) rather than `RgbValue`, and the same type flows through spans, lines and painters. What was settled beforehand:

  - **Resolution as in Helix.** A color is looked up in the theme's `[palette]` first, then read as hex, then as one of the 16 names, numbered as Helix's crossterm backend numbers them (`gray` 8, `light-gray` 7). A style whose `modifiers` hold `reversed` has its fg and bg swapped at load. Token colors are `Color`s too.
  - **The background and the text fall back to the terminal's own colors**, as in Helix, instead of a dark blue and a grey; `iceberg-dark`, `iceberg-light` and `jetbrains_dark` now take the terminal's text color. Theme colors are painted through `ApplyColors` with the whole style, never `SetBgColor`, which cannot clear the pen.
  - **Color arithmetic runs only on RGB.** `ensure_readable_fg` keeps the foreground when either color is the terminal's; `marker_bg` is `ui.selection` then.
  - **Deferred:** asking the terminal for its palette (OSC 4) at startup. Without it a symbol highlight, a fixed RGB background, is not contrast-corrected under a token in a palette color; to add if that proves hard to read in practice.

  Where the implementation differs from what was settled, and why:

  - **No `title` role.** The focused title bar's text is `text`, not `ui.text` with its own constant: on a 16-color theme with no `ui.text`, an RGB title would sit on a palette selection.
  - **No line-number dimming at all.** The plan kept the `/ 3` dimming of the preview and the git log for RGB colors. But `line_number` falls back to `dim`, so with that chain the dimming was never reached; an unstyled `ui.linenr` now takes `dim` in both panes (the `comment` color, else the text color), as the tree already did.
  - **`color_for_scope` returns a `Color`**, since its fallback `ui.text` now always resolves. The constants the call sites kept after it (branch blue, diff colors, tree colors, commit types) were reachable only for a theme that styles neither the scope nor `ui.text`, and are gone; such a theme now gets the terminal's text color there. The git log's fixed orange for a tag stays, for a theme that gives tags and branches one color.
  - **`marker_bg` mixes `ui.warning`** into the background, where it mixed the `warning` scope with a fallback to `ui.text`; the two differ only for a theme with no `warning`, which now gets the constant warning color instead of its text color.
  - **More roles than the table listed**, one per lookup the panes made: `selection_fg`, `line_number_bg`, `line_number_selected`, `cursor`, `matched`, `ruler` (an `Option`: no ruler, no code-block background), `scroll_track` and `scroll_thumb`, whose collision check against the track now runs once at load.
  - **The input cursor uses the terminal's reverse attribute** instead of swapped colors: swapping two colors that are both the terminal's defaults draws no block. The pen is still set before it, which is what made the bare attribute unreliable before.
  - **`exact_fg` stays** as the one string lookup outside the palette, for markdown's `markup.*` scopes, which are text styles and not UI roles.
  - The fixed RGB colors (`SYMBOL_PALETTE`, the search colors, the terminal pane's default selection text) stay `RgbValue`, wrapped in `Color::Rgb` where they meet theme colors.
- [x] **L2. Widgets take values.** `title_row` gets what it paints (title, colors, focus) instead of `&mut AppState`; `FuzzyPickerState` moves from `state.rs` to `widgets/fuzzy_picker.rs`, the one widget that uses its shape. Rule for `AGENTS.md`: `tui/widgets/` imports only `theme`, `util` (`input_line` already uses `util::text`) and other widgets. `fuzzy_picker` also takes `&AppState` (its `display` closure), `&mut PaneManager` (the scroll it sets) and `&Window`: under the rule those become values, which phase 2 designs.

  Done, without a phase 2 design. What was settled beforehand:

  - **The `TitleRow` trait is gone, not moved.** `render_title_row` and `render_input_title` already took values; only the trait named `AppState`. Nothing used it generically (no `dyn`, no bound: `PaneComponent` matches the window and knows each concrete type), and the git log and the Discussion already had the method as a plain one. The eight implementations, and `PaneComponent`'s own, are inherent `pub(crate) fn render_title_row`, dispatched with method syntax.
  - **`FuzzyPickerState` lives in `widgets/fuzzy_picker.rs`.** `FuzzyPicker`'s private copy of `resolve_selected_index` is gone; it calls the state's.
  - **`render_results` takes `&HelixTheme`**, and its `display` closure takes only the key: each caller's closure captures the state it reads.
  - **`publish_geometry` is gone.** `PaneManager::set_window_view(window, scroll, scroll_max, page_size)` sets the three values, and the three pickers call it with the picker's scroll offset.
  - **`cargo xtask check-imports` enforces the rule**: under `src/tui/widgets/`, a `crate::` path outside `crate::tui::widgets`, `crate::tui::theme` and `crate::util` is refused. `AGENTS.md` states it in the widgets entry.

  The color fallbacks of `render_results` this item left for L1 were already gone with it: the widget reads `theme.ui` fields.
- [ ] **L3. Windows are views, and window state leaves the slot.** Accepted, to be done after L7 and before L6. `PaneComponent` holds one instance of each pane kind per slot, so a window lands on another instance whenever its slot in the stack changes, and what an instance keeps follows the slot instead of the window. Two steps:

  1. **The ten child panes stop implementing r3bl `Component`** and become plain structs whose `render`, `render_title_row` and `handle_event` take the window id, the box and `focused` from `PaneComponent`, which already matched on the window to pick the child: e.g. `render(&mut self, global_data, id, content_box, focused)` and `handle_event(&mut self, global_data, id, content_box, focused, event)`. This drops their `get_id`/`reset`, their `id` fields, the six `pane_slot` → `slot_window` lookups (each a `None` check or fallback in a helper that `render`, `render_title_row` or `handle_event` calls) and the four copies of the content geometry kept for the mouse handlers, which take the content box from `PaneComponent` instead (today it keeps only four numbers of that box, from its last render), and the terminal's `slot` field, which `pane_height` reads through `slot_box`. Only `PaneComponent` stays an r3bl `Component`.
  2. **Window-owned caches and messages move to per-window state:** `DocCache` and the Discussion's layout geometry into `DiscussionState`, `ReportCache` into `ReportState`, and the preview's `error` into the per-file preview state, which is keyed by `FileKey` like `search` and `highlight_ranges` (not `PreviewInput`: it exists only while the title bar's search input is open, and Enter removes it right after a bad regex sets the error). Today they follow the slot: the preview's error shows in the title bar of another file after a stack move, and a stack move lays out again each visible Discussion whose window changed slot, at the cost of P1 each time (a push or a send to back changes many at once, a swap changes two). Short-lived interaction state that is cancelled when the window changes, drags and click trackers, stays per slot. The ten instances per slot stay: once the caches leave them they are almost empty.

  The Discussion keeps its own box (`content_box`, scrollbar column included, and `scrollbar_rows()`): its input runs under the scrollbar, which is a behavior of the pane, not plumbing. Step 2 is what makes L6 worthwhile.
- [x] **L4. A `tui::turns` module owns the turn lifecycle.** Dropped. The proposal was one `Turns` struct in `AppState` (running handles, queue, spinner frame, `after_agents` and its grace and counter) and one module with `start`, `finished` (the `TurnFinished` arm), `release_queue`, `take_back`, `stop_all` and the `after_agents` arming. It would move code without removing a dependency:

  - **The lifecycle is window logic by design.** The queue holds the window, and the text stays that window's `draft` until its turn starts (`AGENTS.md`): `release_queue` composes each prompt from its window's draft and writes refusals into its `notice`, `send` and `inject` read and clear the draft, `restore_injected` puts unread messages back into one, and the end of a turn updates each window that shows the node. A `tui/turns.rs` would import `DiscussionState` and `DiscussionComponent` as heavily as `launch.rs` does.
  - **Every caller is Discussion code or acts on a Discussion window.** `start_turn` and `launch_window` are called only from there; outside it, the tree calls `take_back` and `take_back_window` (about a queued window) and `focus` calls `drop_queue_entry`. No second subsystem starts turns.
  - **`launch.rs` already is the turns module**: `TurnKind`, `Launch`, `Refusal`, `start_turn` and the refusal rules, apart from the pane's rendering and input code. A `Turns` struct would only rename about 50 `running_turns` / `queued_turns` sites, and the `after_agents` fields are already owned by `after_agents.rs`, which writes them, and the `after-agents` command of `command_line.rs` also sets `after_agents`; no turn code writes them. `resume_of`, `interrupted_of` and `node_mode` read only node metadata and can already be tested without an `AppState`.

  Kept from it, in one commit:

  - **The end of a turn is `DiscussionComponent::turn_finished`** in `discussion/queue.rs`, next to `release_queue`; the `TurnFinished` arm of `app/signals.rs` only calls it. `spawn_dirty_check` became `AppState::spawn_dirty_check`, since a pane never imports `app/`.
  - **`lock_refusal` is gone.** It took the modes of the running turns but only checked that there was one, a remnant of the shared lock feedback turns once had; `start_turn` refuses directly when any turn is running.
  - **`node_model` is gone.** It wrapped `Metadata::model_spec` in one line; the model picker and `signals.rs` call `model_spec` themselves.
- [ ] **L5. `pane_manager` keeps layout only.** `DocPart` moves to `panes/discussion/`, `SelPoint` and `TextSelection` to a `tui/selection.rs` (the preview, the terminal and the Discussion all use them), and `block_scroll`, `ranges_scroll_target` and `format_line_ranges` to `panes/preview.rs`: they are about line highlights of a file, and only the preview and the command line's `highlight` call them. What stays: `Window`, `PaneSize`, the stack, focus order, `relayout` and the per-window scroll.
- [ ] **L6. Window state grouped by window.** The parallel maps of `AppState` become one `windows` struct (`previews` for `preview_inputs`, `terminals` for `terminal_panes`, the others under their own names) with `close(window)` and the session's walk over it as methods, so the knowledge of which map a window kind owns is in one place instead of in `focus.rs`, `session.rs` and the pane files. With L6, `AppState` drops from 52 fields to 47 (L6 takes six out and adds one). It is worth doing only with L3, whose step 2 moves the window-owned caches into these per-window states, and comes after it.
- [ ] **L7. Routers, not bodies, in `app/signals.rs` and `app/input.rs`.** Each arm of `signals::handle` that is more than a few lines moves to the module that owns the state it changes (`git_log_pane::log_loaded`, `conversation_tree::loaded`, …, as `DiscussionComponent::turn_finished` already is for `TurnFinished`), leaving a match that only dispatches. Same for `input::handle`. No behavior change; the 419- and 236-line functions become tables.
- [ ] **L8. Break the subagent cycles inside `agent`.** `tools` ↔ `subagent` and `agent_loop` ↔ `subagent` come from the `agent` tool, which runs the loop again. Proposal to evaluate in phase 2: the `agent` tool's spec and dispatch live in `subagent`, and `tools` stops naming `subagent`; `context` stops reaching into `agent_loop`: its one call there is `repair_tail`, in `ancestor_messages`, which phase 2 finds a home for. Accept only if it removes the cycles without a new indirection (no trait object or callback added just to break them). The `tools` ↔ `mcp` cycle is not covered by this item; phase 2 proposes its own cut.

## Performance findings made while mapping

Reasoned, not measured. Each names how often it runs. Most are small; the first two are the ones that grow with use.

- [ ] **P1. The reply of a running turn is laid out again in full on every frame that it grew.** `panes/discussion/document.rs` `doc_lines` rebuilds `doc.reply` with `widgets::markdown::render(&discussion.reply, …)` whenever `reply_len` changed, and `thinking` with `push_wrapped` over the whole text whenever `thinking_len` changed. While a turn streams, the turn tick alone repaints it up to 10 times a second, each repaint costing the whole reply: quadratic over a turn. The previous review measured a 71 KB report at 3.3 ms per layout, so a long reply costs that 10 times a second. Fix to design in phase 2: lay out again only from the start of the last top-level markdown block, keeping the lines before it. That needs care: the text before the last blank line outside a fence is usually final, but a link reference definition later in the reply, or a list item after a blank line that makes the list loose, can change how earlier text renders, so phase 2 has to say how the renderer handles both. The same goes for thinking: lay it out again only from its last wrapped line.
- [ ] **P2. A running turn repaints every visible pane 10 times a second.** `TurnTick` lets the frame through whenever a turn runs, and the frame rebuilds all panes. Most frames change only the spinner, the Discussion of the turn and the tree row. Not a reason to touch the tick (decided), but a reason to make each pane's render cheap when nothing changed for it: P3 to P7 are the parts of each pane's render.
- [ ] **P3. The frame fills most of its background twice.** `app/render.rs` fills the whole surface row by row (`" ".repeat(cols)` per row), and then most panes fill each of their rows again before painting their content (`preview.rs` per sub-row, `discussion` input rows, `terminal` blank rows, `title_row`). Paint the app-wide fill only where no pane is (the gaps between panes), or drop the per-pane fills where the stylesheet's `color_bg` already covers the box. The stylesheet itself (`create_stylesheet`, 33 styles) is rebuilt every frame and could be rebuilt only when the theme changes.
- [ ] **P4. Per-row and per-span allocations in the file preview.** Per painted row: `" ".repeat(pane_width)`, a `format!` for the line number, and another `repeat` for a wrapped line's gutter. Per segment: a `ui_fg("ui.text")` lookup (gone with L1: it is a field read now). Per syntax span: `ensure_readable_fg`, i.e. two luminance computations, for a pair (token color, background) that has a handful of values per frame. `InlineString` holds 16 bytes inline, so a row-wide text wider than that is a heap allocation in r3bl too, twice when it goes through a `String` first.
- [ ] **P5. The conversation tree is flattened again on every frame.** `conversation_tree/layout.rs` `rows` rebuilds `layout_rows`, `with_queued` and `with_agents` (one `rails` vector and cloned `NodeId`s per row) on each render, and the input handler builds them again for each key. Only the filter path is cached (`FilterCache`). Cache the unfiltered rows on the tree's `revision`, the expanded and shown-agent sets, and the queue, as the filter already does.
- [ ] **P6. Small per-frame copies in the Discussion.** `discussion::render` copies each part's highlights (`highlights.part(part).to_vec()`, four times a frame) only to hand out slices; `state::append_str` copies the appended text into a temporary `String` before pushing it (`live[text.len()..].to_string()`), on every frame the reply grew.
- [ ] **P7. One `String` per style run in the terminal.** `terminal/mod.rs` `render_lines_to_ir` builds a fresh `String` for each run of cells with one style, and one more per cursor cell (`ch.to_string()`), on every frame for every visible terminal; `render` also collects the visible rows into a `Vec` each frame. Build into `InlineString` directly.
- [ ] **P8. The status bar allocates its hint every frame.** `app/status_bar.rs` turns fixed hints into `String`s (`"Esc:Close picker  Enter:Open  …".to_string()`) on each frame; a `Cow<'static, str>` or `&'static str` does it without allocating.

Checked and fine, not to be chased again: `widgets/fuzzy.rs` reuses its query, matcher and char buffer across items; the window picker matches off the main thread and keeps only the newest generation; the streaming path (`Recorder::text`) calls `Recorder::flush_reply`, which clones and rewrites the whole reply, at most once a second (a tool call and the end of a turn flush too); `Throttle` stops a burst of terminal output from flooding the main channel once a send has failed, and reopens after a 100 ms pause.
