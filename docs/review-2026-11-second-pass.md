## Steering with Claude Code

- [ ] **S1. Close a Claude Code run only when its background tasks are done.** `src/agent/claude_code.rs` (`run`, `parse_line`), `src/agent/turn/live.rs` (`LiveTurn.closed`). The driver treats the CLI's first `result` line as the end of the run: within 250 ms it closes stdin and sets `live.closed = true`. Current Claude Code often keeps going: background tasks (agents, background Bash) finish later, the CLI gets a `<task-notification>` and starts another model turn. The window shows the turn as running for minutes, but `inject` refuses every message (`if live.closed { return false; }`) and `send` queues it as a new turn. Seen in session `327a9054`: first `end_turn` 30 s in, task-notification turns for 3 more minutes. It predates the refactor (`062b513`, `865d93d`, `414a4e9`). Fix: `parse_line` maps `{"type":"system","subtype":"task_started","task_id":…}` to `StreamEvent::TaskStarted(id)` and `{"type":"system","subtype":"task_notification","task_id":…}` to `StreamEvent::TaskDone(id)`; `run` keeps the set of outstanding task ids; `TaskDone` also clears `settled`, since the CLI answers the notification with another `result`; close only when `settled && outstanding.is_empty()`. Test the parsing and the close rule.
- [ ] **S2. Reopen the injector at the start of every run.** `LiveTurn.closed` is never reset. The commit-nudge runs (`turn/mod.rs`, around `:357`) and the retry after `SessionGone` (`claude_code.rs`, around `:75`) reuse the recorder of the previous run, already closed, so a commit turn cannot be steered during its nudges. Fix: add `Injector::open()` (it does not exist yet), which sets `live.closed = false`, and call it at the start of `run`, before the first write.

## Regressions from the refactor

- [x] **R1. A `features` change reopens every file ever opened.** `src/lsp/worker.rs` (`restart_server`, around `:270-300`, step 13). After the change it sends `didOpen` and full token requests for every file the warmup opened (every `.rs` file, never closed), back to back without draining stdout: the pipe deadlock `send_warmup` exists to avoid, and a duplicate of the paced warmup re-queued just above. Fix: delete the reopen loop, and re-request only the open `FilePreview` windows instead, as `1d073ff:src/tui/app.rs` (around `:1785-1815`) did after its restart: `lsp::send_file_request` for each `Window::FilePreview` in the window stack, sent once the new worker was subscribed. At HEAD nothing does this: the `SetCargoFeatures` arm in `src/tui/app/signals.rs` only stores the selection, so the new code has to add it, ordered after the restart. Done: `restart_server` drops the `reopened` collection and its loop, leaving the warmup re-queue as the only path re-requesting what it opened; the `SetCargoFeatures` arm asks again for every `Window::FilePreview` of the window stack right after `lsp::set_cargo_features`, so the restart precedes them in the worker's queue (or in the buffer, which is replayed in order). Left undone: no test covers a restart itself (it needs a real Cargo project and would flake, and driving `signals::handle` would leak entries into the process-wide request buffer); a manual `features` run should confirm the new server gets one paced warmup and no `didOpen` burst.
- [x] **R2. An engine restart forgets the selected cargo features.** `src/lsp/mod.rs` (around `:38-44`), `src/tui/app/signals.rs` (around `:56-60`) (step 13). Any engine-level restart (rust-analyzer crash, read error) rebuilds the worker from the startup config; the features revert while the UI still shows the new selection, and a code comment admits it (`src/lsp/worker.rs` around `:296-298`). Done: a process-wide store in `src/lsp/mod.rs` (`CARGO_FEATURES`, `cargo_features`, `set_cargo_features`), read by `create_and_register_os_sources`; `restart_server` needed no change since it spawns from the selection it is given. Three deviations from the plan: **an `Option` behind a `parking_lot::const_mutex`, not an `ArcSwap`** — `None` says "no command has selected anything yet" and makes the seed fall back to the config the worker was subscribed with, so a fresh start still honours the session's saved selection without seeding the store at subscription; **the store is written when the command is issued, not when a spawn succeeds** — a selection rust-analyzer refuses to start under is kept (as `restart_server` keeps the old process) and retried once more by the next engine restart, within the engine's budget of 3, where storing on success would keep the last working selection at the cost of a `remember` call in `restart_server`; and **`LspConfig::cargo_features` stays** as the seed, so `src/tui/app/init.rs` is untouched.
- [x] **R3. Overlapping watcher batches lose or duplicate files.** `src/watcher.rs` (around `:206`), `src/loader/watch.rs` (around `:63-190`) (step 22). Paths are resolved to keys on the watcher thread against the list as it was, and swapped in later on the main thread. When two batches overlap (the main thread takes more than 50 ms), a file created in batch 1 and modified, removed or re-created in batch 2 loses the edit, outlives its deletion, or is appended twice. Fix: keep reading on the watcher thread, but resolve paths to keys in `swap_in` against the current list, and check that an appended path is not already present. Test the overlap. Done: the read keeps the key it found only as a hint and carries the path, and `swap_in` resolves every path again through `resolve_key` — the read's key when it found one, since the list is append-only, else the first match in the tail grown since `Pending::read_len`, so an overlapping batch appends nothing twice. `resurrected` and `appended` merged into one `created` list, decided at publication since only the list then knows whether a path is new; `read` now reads through `read_file_data` everywhere, never `LoadedFile::load`, so a file is read once (`LoadedFile::from_data`). Three tests cover the overlap: an edit lands, a deletion marks removed, two `created` batches append once. Left until later: the read still skipped an edit to a file the list flagged removed when the read ran, so a file brought back by an unpublished batch and edited before that publish lost the edit; `read` now keeps the key of every path of `batch.modified` and `swap_in` drops the edit only where the file is still flagged removed at publication, and `an_edit_of_a_file_brought_back_by_an_unpublished_batch_is_applied` covers it.
- [x] **R4. Tab escapes the command line when its palette is empty.** `src/tui/command_line.rs` (`CommandLine::handle_event`, Tab and BackTab arms, commit `5dda7ee`). With no palette entries (after any space, after `!`, or on an exact command name) the arms fall out of the `match`, and the global keymap cycles pane focus behind the open line. Fix: return `true` after the `if !entries.is_empty()` block in both arms. Done: both arms return `true` whatever the palette holds, as the catch-all arm did before `5dda7ee` took the guard off the arm; `tab_stays_with_the_line_when_the_palette_is_empty` covers Tab and Shift+Tab.
- [x] **R5. A Discussion opened on a running turn shows stale content.** `src/tui/state.rs` (around `:223`, `:250-257`) (step 16). The first render copies the live turn and records `live_revision`; then `NodeContentLoaded` → `show_content` replaces the texts with the disk copy without resetting it, so `mirror` skips copying until the turn next changes, which can be minutes during a long tool call. Meanwhile there is no thinking, dropped rounds reappear, and the reply can be up to 1 s old. Fix: `self.live_revision = 0` in `show_content` and in `apply_sent`. Done: `live_revision` is an `Option<u64>`, `None` until the running turn's texts are taken, and `show_content` sets it to `None`, so the next render mirrors the live turn again; `texts_replaced_from_disk_are_taken_again_from_the_running_turn` covers it. Two deviations from the plan. **`Option`, not `0`** — revision 0 is what a live turn carries before anything touches it, so zeroing the field could collide with a real revision and skip the copy again; `None` is also what `Default` gives, which is right for a window that has copied nothing. **`apply_sent` is left alone** — revisions come from one process-wide counter (`live::REVISION`), so a turn started after the window copied another cannot carry the number it holds.

## Behavior changes to keep or revert

These looked fine to the review; the owner decides. Nothing to do unless one is reverted.

- [ ] **C1. Idle wakeups.** The 100 ms spinner tick (step 15) runs for the whole session and renders only while a turn runs, so an idle app wakes 11 times a second instead of once. Proposed: run the tick only while `running_turns` is non-empty.
- [ ] **C2. `fmt-md .` still formats the whole repository.** The guard from `2352de8` refuses `""` only. Either refuse any path that resolves to the repository root, or drop the guard.

Accepted as they are:

- LSP token colors (B4, intended): `comment`, `modifier`, `const`/`static`, `namespace`, `parameter`, `property`/`enumMember` and `lifetime` now use their more specific scopes (`comment` used to be painted in the string color).
- Session save runs on the 5 s housekeeping tick instead of 2 s after the last change; the save on exit is unchanged.
- The report pane gained Up/Down/Home/End/Ctrl+A/E, the commit diff Ctrl+A/E.
- Focus repair during a render releases the terminal grab and sends focus-in/out bytes, consistent with the grab rule.
- The watcher drops an unreadable file of a batch instead of keeping its old content.
- Config and auth paths need a UTF-8 home directory, as conversations already did.

- [x] **H4. Step 12 / B5: cancel running sub-agents on quit.** The exit loop never calls `cancel_running_agents`, so a sub-agent running at quit loads as `Failed "interrupted"` next time. Predates the refactor; one line next to `mark_cut_short` in the exit loop (`src/tui/app/mod.rs` around `:250`), called as `agent/turn/mod.rs` does around `:179`. Done: the loop is `stop_running_turns(state)` in `src/tui/app/mod.rs`, and it calls `tree.cancel_running_agents(node, now_secs)` right after `mark_cut_short`, so the runs of a turn a quit cut short are settled by the same rule as the runs of one that ended on its own.
      **The concern was valid as reported, and one step worse.** The run loaded as `Failed`/`interrupted` because `metadata::read` treats a `running` status as an unfinished run of a previous instance; but the same read is what gives it that status, so the run also lost its **duration**, which only a cancel records (from its `created` stamp). A run left running was also the only record of the turn's subtree that a quit did not settle: the node was marked, its runs were not.
      **The statuses can still differ, and that is intended.** The node and its run are judged on their own content, not on each other's: a sub-agent's text is split out of the turn's `reply` into its work log while the tool call runs (`Recorder::answer_calls_tools`), so a turn stopped mid-sub-agent usually has no reply of its own and records `Failed`/`cancelled by the user` — a rule a feedback turn would go through on its own too. A run that streamed a partial answer records `Cancelled`, and one that did not records `Failed`, exactly as `cancel_running_agents` decides for a turn that ends normally. This commit makes the exit path reach the same rule; it does not make the two statuses equal, and it must not.
      **Deviations from the report.** (1) The report said "one line next to `mark_cut_short` in the exit loop". It is one line, but the loop was an inline block inside `run` with no way to reach it from a test, so it became the free function `stop_running_turns(&AppState)`; the exit path's only other statement is the call. That is the whole reason for the function — the exit path had no test at all and this is its first. (2) `TurnHandle::for_test` in `src/agent/turn/mod.rs` (behind `#[cfg(test)]`, built on the existing `LiveTurn::for_test`) exists so the test can park a handle in `running_turns` without spawning a turn; it is the same kind of hook as `AppState::for_test`, which the test also uses.
      **Not covered.** The exit path as a whole is still untested — reaching `stop_running_turns` through `run` needs the TUI event loop. What is tested is the rule: one running turn with a run under it, and the run comes out `Cancelled` with its reply kept and a duration, where without the added line it stays `Running` (verified by deleting the line and watching the test fail). A run's reply is read back from `reply.md` (the last flush, up to 1 s old), where the turn's own is taken from the live text in memory; so a run whose last second of answer never reached the disk loses that second at quit, and the turn does not.
- [x] **H5. Step 23: `retitle_selected` reads `reply.md` before the cheap checks.** Do the checks first. Done: `needs_retitle` takes `has_reply: impl FnOnce() -> bool` and asks it last, after the title, status, retitling and commits checks, so `read_reply` runs only when none of them has already answered; the caller passes a closure, and `a_node_whose_status_already_answers_is_not_asked_for_its_reply` counts the closure's calls to pin that, for each of the five ways the rule can be settled without it — a title, a `done` status, the retitling set, the commits, or a running turn.
      **Why not "do the checks first" at the call site.** Hoisting the status test into `retitle_selected` would have put the rule in two places — the caller deciding worth, `needs_retitle` deciding it again for the seven cases its test walks — which is how such a pair drifts. The closure keeps one rule in one function and still makes the read unreachable when the answer is already known: passing an eager `bool` no longer compiles, since the signature demands a closure.
      **What the read cost, measured** (release build, this machine's tree): 4.8 µs for a 15 KB reply, 1.1 µs when there is none, and it ran under `state.conversations.read()`, the `parking_lot::RwLock` the background tree load takes for writing. This repository's own tree (`ConversationTree::load` over its `conversations/` directory) holds **295 nodes and 10 untitled ones, of which 1 could not have used the answer** — a `done` node beside 8 `failed` and 1 `cancelled` that legitimately need the read. So this buys 4.8 µs, once per selection that lands on such a node: worth fixing because the read is pointless and sits under a lock, not because it shows up in a profile. Two counts before it were wrong and are worth recording: counting every conversation on the machine rather than this repository's, and counting without pruning `agents/`, which `load_children` never treats as nodes.
      **Deviations from the report.** (1) The report said to do the checks first; the closure does that without splitting the rule, as above. (2) Conjunct order was changed beyond the minimum: `!retitling.contains(id)` moved from after the bracketed group to ahead of it, because a node whose retitle is already running must be turned down without asking for its reply — where it sat, after the group, the file was read first. (It is not the cheaper test there: a `HashSet` probe against a `Vec::is_empty`; it moved for the read, not for the clock.) (3) The read is still synchronous and still under the lock: moving it off would need a channel round-trip and a state machine for a value that is usually absent. Dropping the guard around the read (clone `node_dir`, drop the tree guard, then read) is an independent improvement and was left alone here.
      **Not covered.** No test exercises `retitle_selected` end to end (it spawns a task against a real summary model); the new test pins the rule, which is where the read lives. A failed node with no commits and no reply is still asked once — that is the case the read exists for.
- [x] **H6.
