---
title: Themes and colors
summary: How a Helix theme becomes Explorer's colors: the generated table, the three kinds of color, and the precomputed token colors.
refs: src/tui/theme.rs, HelixTheme, Ui, Color, color_for_scope, token_color, scopes, TokenKind, themes/themes.rs
---

`src/tui/theme.rs` turns a bundled Helix theme into the colors Explorer paints with. `include!("../../themes/themes.rs")` compiles the generated theme table in; `HelixTheme` parses one theme and its inheritance chain, and `from_name` caches the built result, since parsing takes a fraction of a millisecond that a live theme preview cannot afford on every frame.

`Color` is `Rgb`, `Ansi(u8)` or `Default`, because a Helix theme names a color three ways and each reaches the screen differently: a hex value is painted as is, one of the sixteen is a terminal palette index, and `default` means the terminal's own choice regardless of the pane's background.

`Ui` names one field per Explorer surface role (background, selection, line numbers, matched text, error, warning, status bar, prompt, scrollbar, overlay…), each documenting which theme keys it reads, so a theme that styles a role differently still lands in the right place. `color_for_scope` walks a dotted scope's parents, which is how a scope with no exact rule still gets the theme's nearest color, and falls back to `ui.text`; it never returns "no color". `token_color` is the one that can: it returns `None` when the theme styles none of the token's scopes, and the token keeps the pane's color.

That last one is resolved once, at `build`: `token_colors` is an array indexed by `TokenKind`'s discriminant, filled from the first scope in `kind.scopes()` the theme styles. The scope lists are most specific first, so a bundled theme that styles `type.builtin` but not `type` still colours a type, and painting a span is an array read rather than a chain of string lookups per frame.

`themes/themes.rs` is generated by `cargo xtask update-themes` and must not be edited by hand.
